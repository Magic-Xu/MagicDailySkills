# 深入审查指引

按当前疑点选择相关部分；检查结论留在任务对话中，除非用户要求审计产物。

## 读者与使用路径

明确谁在什么场景打开产物、已有知识、要完成的动作或判断，以及下一步。无法说明这些问题时，不能用“读者可能需要”作为保留内容的理由。

对 README、快速开始、指南和 UI 文案，沿常见读者的使用路径检查：

- 先提供可成功的基本路径，再说明会影响操作或选择的前置条件、分支和风险。
- 每段应帮助读者执行动作、理解必要概念或避免真实错误。真实但不服务此处任务的信息应移到适当位置。
- 内部实现提醒、未采用方案、Agent 自我约束，只有会直接影响读者的选型、兼容性或数据安全时才写入。
- 标题和措辞用读者自然使用的语言，避免抽象术语、直译问句和内部争论打断主路径。

首次使用文档走查一遍：读者能否理解用途、完成最小示例，并找到相关分支。仅复查本次改动影响的路径，无需机械重读无关章节。

## 需求与比较基线

从当前请求和后续决定确定有效需求，不把完整对话当作规格。仅在尚存歧义会改变产物语义时询问。

- 状态型产物表达当前行为和持续约束。
- 变更型产物选择对应的任务起点、合并基线或上一发布版本；当前 HEAD 不一定是正确基线。
- 过程型产物保留其用途需要的取舍、证据和结论。

Git 审查包括本任务的已提交差异、新增文件与工作区改动；区分其他任务和用户原有内容。非 Git 产物检查本任务对象及其直接影响的内容，不扩展成无边界的全库审计。

## 可疑内容的判断

对可疑文字、命名、行为、测试、配置、视觉资源和元数据，核对：它是否真实、服务哪个读者动作、是否放在正确位置，以及是否对应有效需求或真实变更。

“如果中间错误从未发生，这段内容是否仍有必要”只能用于发现疑点。真实回归测试、长期 workaround、安全或兼容性约束仍可能必要；以用户确认、既有规格或行为、适用规则等独立证据判断。

## 修复边界

修复继承原任务的对象与授权，不自动包含删除产物、修改非本任务内容、改写历史或修改外部 PR 与发布。删除会改变产品语义或无法判断是否为长期约束时，先澄清。修复后只复查受影响内容，不为证明检查有效而新增测试、检查器或永久规则。
