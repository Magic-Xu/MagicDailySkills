# 产物边界检查

在用户明确要求审查现有产物时运行；也在任务创建或修改了持久化产物、完成常规验证且即将最终交付时运行。纯问答或没有待审产物的任务不运行。

目标是让产物只表达目标读者完成当前任务所需的有效需求、真实终态、实际变化和持续约束，不把形成这些结论的对话过程误写进产物。事实真实只是保留的必要条件，不是充分条件。

## 建立审查基准

1. 从当前请求和后续确认中提炼一份内部“最终有效需求”，区分：
   - 已确认的目标、最终决定和验收标准。
   - 当前作用域内持续成立的产品或工程约束。
   - 已被否决、替换或撤回的方案，以及仅由本轮误解产生的限制。
2. 为每类面向人的产物先写一份内部“读者任务契约”：谁会在什么场景打开它、此时要完成什么动作或判断、已经知道什么、读完后下一步是什么、哪些维护过程或内部争论与此人无关。不能明确这些问题时，不得用宽泛的“读者可能需要”作为保留理由。
3. 确定每类产物的用途和比较基线。状态型产物以预期终态为准；变更型产物按其用途选择合并基线、任务起点或上一发布版本，不得默认当前 `HEAD` 就是正确基线。Git 仓库用工作区 diff、已提交的分支差异及本轮新增文件定位候选；先区分本任务引入的改动与用户原有或其他任务的改动，不得默认整个 diff 都归本任务所有。非 Git 任务检查待审产物及本轮直接影响的相关产物。
4. 读取适用的 `AGENTS.md` 和项目规则，但不要把一次纠正自动解释成新的永久规则。

不要把完整对话直接当成产物需求。无法确定哪条指令仍有效，且不同解释会改变产物语义时，停止并询问用户。

## 区分产物类型

- **状态型产物**：代码、UI、README、测试、配置、命名等，表达当前真实状态和持续成立的不变量。
- **变更型产物**：提交信息、PR、发布说明、变更日志等，表达相对既定基线真实发生的变化。
- **过程型产物**：ADR、复盘、审计、调试记录等，按其用途记录必要的决策或调查过程。

同一段内容在不同类型中可能有不同结论。不要用状态型产物记录无关历史，也不要从本来以记录过程为目的的产物中删掉必要过程。

## 面向使用者的产物

README、快速开始、使用指南、UI 文案等面向使用者的产物，先按读者完成任务的顺序审查，而不是按作者想解释的知识顺序审查：

1. 先给最常见读者一条最短可成功路径，再补充确实会影响其选择的分支、前置条件和风险。
2. 每段都必须能对应读者此刻要做的一个动作、要理解的一个概念或要避免的一个真实错误。无法说出具体作用时，删除、移到维护/审计文档，或改写成能直接帮助读者的内容。
3. 不向使用者罗列“没有做什么”、被否决方案、内部能力候选或 Agent 自我约束，除非使用者会合理期待该能力，且不说明会直接导致错误选型、数据风险或兼容性损失。
4. 不把作者侧的实现提醒直接写成读者侧命令。只有违反后会产生真实问题且读者容易遇到时，才保留为具体后果和处理方式。
5. 标题应直接说明本节帮助读者完成什么，正文使用目标读者自然会说的语言。避免直译式标题、抽象名词堆叠、内部术语串联和为了显得完整而追加的否定清单。

首次使用文档至少走查一遍实际阅读路径：读者能否顺序回答“这是什么、先添加什么、最小示例怎么跑、核心语义是什么、遇到分支去哪里看”。后续维护、版本取舍和未采用方案不得打断这条路径。

## 语义检查

检查本任务拥有的文字、注释、标识符、可执行行为、测试、配置、模式或迁移、生成物、视觉资源和元数据；同时检查因本轮变化而直接失真的相关产物，但不要扩展成无边界的全仓审计。对每个可疑内容依次判断：

1. 它服务读者任务契约中的哪个具体动作或判断？无法明确回答时，为什么还应出现在这里？
2. 它描述的事实在最终状态下是否真实？
3. 目标读者是否需要在当前位置、当前阶段知道它，而不是维护者或另一篇文档需要？
4. 对变更型产物，它是否对应基线到最终状态的实际变化？
5. 对规则或测试，它是否表达可验证且持续成立的约束？
6. 对面向人的文案，它的标题和表达是否像目标读者会自然理解的语言，是否能直接导向动作或判断？
7. **如果本轮错误尝试从未发生，这段内容是否仍有必要存在？**

第 7 问只用于标记嫌疑，不能单独决定删除；必须结合前六问、产物类型和现有证据判断，避免误删 ADR、复盘、真实回归测试或仍在生效的 workaround。一次错误可能暴露此前未成文但真实存在的不变量；只有用户确认、既有规格或行为、适用规则、安全/兼容性要求等独立证据支持时，才把它视为持续约束。

重点寻找：

- 已否决方案、中间尝试或先添加后撤销的内容仍残留在名称、注释、测试或说明中。
- 产物解释了 Agent 的工作过程、纠错、自检、fallback 或与目标读者无关的限制。
- 面向使用者的文档罗列未采用能力、内部边界争论或维护者约束，却不能改变读者当前的操作或选型。
- 快速开始在最短成功路径之前讲实现细节、替代分支或作者侧提醒，增加了首次接入成本。
- 标题只是抽象概念或直译式问句，正文堆叠内部术语，读者看完仍不知道下一步做什么。
- 为证明本轮错误不会重演而新增的测试、检查器、规则或警告，但它们并不对应真实的长期不变量。
- 提交、PR 或发布说明描述了相对基线并未发生的变化。
- 未确认的用户偏好、推断或临时选择被固化成长期约束。

文本搜索只能帮助发现候选，不能作为删除依据。不得使用硬编码禁词、正则命中或历史错误清单替代语义判断。

## 处理结论

保留以下内容：

- 当前有效需求和真实终态。
- 相对基线确实发生的变化。
- 有证据、可验证且持续成立的产品、安全、兼容性或工程约束。
- 目标读者完成使用、判断或维护所必需的信息。
- 过程型产物按其目的必须记录的取舍、证据和结论。

删除或改写只因对话、中间尝试、纠错过程或本轮误解才存在的内容。真实但不服务当前读者任务的内容也应删除或移到合适产物。不要因为安全、兼容性或迁移约束采用否定表述就误删；先判断它是否真实、持续成立，并且读者需要在这里知道。

修复权限继承当前任务：

- 原任务已授权修改相应对象时，只对可归因于本轮、可逆且结论明确的本地产物做最小修复。一般的编辑授权不自动包含删除产物、改写提交历史或修改外部 PR、发布与其他系统。
- 用户只要求审查、解释或报告时，保持只读，指出具体位置和最小修改建议。
- 删除会改变产品语义、影响非本轮内容，或无法判断是否为长期约束时，停止并询问用户。

不要为了证明检查有效而新增仓库内质检报告、测试、检查器或规则。该检查不替代功能测试、构建、视觉检查、安全审查或领域验证。

## 完成

修复后复查受影响内容；面向使用者的产物还要按读者任务契约从头走一遍，确认没有由作者过程、内部约束或机器化表达打断主路径。不递归调用本 Skill，也不无限循环。同一问题经过两轮修复仍存在时停止，报告阻碍或请求用户判断，不得声称已通过。最终回复只说明是否通过、已修复的实际问题和仍需用户决定的歧义；没有问题时简洁说明已通过即可。
